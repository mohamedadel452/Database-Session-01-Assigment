1) تحويل الكيان البسيط (سلايد 9 إلى 11)

القاعدة: Simple entity (مفيش weak ومستقل) يبقى جدول واحد، وكل attribute يبقى عمود، والـ key attribute يبقى PRIMARY KEY.

-- ERD: EMPLOYEE(EmpID, EmpName, Email, Phone, HireDate)
CREATE TABLE Employees (
    EmpID    INT           NOT NULL PRIMARY KEY,
    EmpName  NVARCHAR(100) NOT NULL,
    Email    NVARCHAR(256) NOT NULL UNIQUE,
    Phone    NVARCHAR(20)  NULL,
    HireDate DATE          NOT NULL
);
INSERT INTO Employees VALUES (1,'Ali','ali@example.com','0123456789','2022-01-15'),
                             (2,'Omar','omar@example.com','0109876543','2022-03-10');

إيه اللي بيحصل فعلياً لما تنفذ CREATE TABLE؟ الـ DBMS بيسجل التعريف في system catalog، وبينشئ clustered index على الـ PK (في SQL Server الافتراضي) فالصفوف بتتخزن مرتبة على EmpID، وبينشئ index فريد للـ UNIQUE على Email. ده سبب إن الـ PK أسرع عمود للبحث.

ملاحظات السلايد 11 مع الشرح

  • "كل entity جدول، وكل attribute عمود": صح، لكن ممكن كيانين يتدمجوا في جدول واحد (1:1 بسيط) أو كيان يتوزع (vertical partitioning) للأداء.
  • "الـ PK يعرّف الصف": ولازم يكون NOT NULL ومستقر.
  • "أنواع بيانات مناسبة": القرار ده بيتحدد وقت الـ mapping (جدول القسم 7).

أخطاء شائعة في الاسم: جدول اسمه User أو Order أو Group كلها كلمات محجوزة في SQL. هتحتاج تكتبها [Order] في كل استعلام. استخدم أسماء مش محجوزة (Users و Orders و UserGroups)، وده كان مطلوب تطبيقه حتى في الجدول في سلايد 23 (جدول ORDER).

// EF Core: الكلاس نفسه
public class Employee
{
    public int EmpID { get; set; }                 // اتفاقية: Id أو ClassNameId → PK تلقائياً
    public string EmpName { get; set; } = "";
    public string Email { get; set; } = "";
    public string? Phone { get; set; }             // ? = nullable
    public DateOnly HireDate { get; set; }
}

2) Simple Attribute (سلايد 13)

القاعدة: عمود واحد بنفس اسم الخاصية. لو هي الـ identifier تبقى PK. (مثال السلايد: STUDENT(StudentID, Name, Email, BirthDate)).

القرار المخفي: هل الخاصية فعلاً simple؟ Name لو هتحتاج الفرز بالـ LastName، فهي composite. وStatus لو قيم ثابتة قليلة استخدم TINYINT + CHECK أو جدول lookup.

CREATE TABLE Orders (OrderID INT PRIMARY KEY, Status TINYINT NOT NULL CHECK (Status IN (0,1,2,3)));   -- 0 New, 1 Paid, ...
-- أو lookup:  Status → FK لجدول OrderStatuses(StatusID, Name)  (أفضل لو الأسماء بتتغير من الـ UI)

3) Composite Attribute (سلايد 14)

القاعدة: نفصّل لأجزاءه الذرية، وكل جزء عمود: Address → Street, City, ZIP. (ما ينفعش نعمل عمود Address + أعمدة الأجزاء، ده تكرار).

CREATE TABLE Employees (
    EmpID INT PRIMARY KEY,
    Street NVARCHAR(100) NOT NULL, City NVARCHAR(60) NOT NULL, ZIP NVARCHAR(10) NOT NULL);
SELECT * FROM Employees WHERE City = N'Alexandria';        -- بحث بالمدينة بسهولة وبـ index
// EF Core: OwnsOne
modelBuilder.Entity<Employee>().OwnsOne(e => e.Address);   // أعمدة Address_Street ... في نفس الجدول

مشاكل متكررة: (1) عنوان في عمود واحد "10 St., Cairo 11511": مستحيل تفلتر بالمدينة ولا تتحقق من الـ ZIP. (2) ZIP كـ INT: بتفقد الصفر الأول في دول كتير. (3) تفصيل أكتر من اللازم (Building, Floor, ...) لمجرد التفصيل يعمّق الجدول من غير فايدة، فاتبع احتياج البحث والعرض فعلاً.

4) Derived Attribute (سلايد 15)

القاعدة: ما نخزنهاش، نحسبها وقت الحاجة من الأصل (Age من BirthDate). السبب: بتتقادم وبتتضارب مع الأصل (update anomaly).

-- الصيغة اللي في السلايد "CurrentDate - BirthDate" تقريبية. الحساب الدقيق للعمر:
CREATE VIEW vw_EmployeeAge AS
SELECT EmpID, BirthDate,
       DATEDIFF(YEAR, BirthDate, GETDATE())
       - CASE WHEN DATEADD(YEAR, DATEDIFF(YEAR, BirthDate, GETDATE()), BirthDate) > GETDATE() THEN 1 ELSE 0 END AS Age
FROM Employees;
-- ملحوظة: DATEDIFF(YEAR,...) بتعد حدود السنين مش السنين الكاملة

// EF Core
modelBuilder.Entity<Order>().Property(o => o.LineCount).HasComputedColumnSql("...");   // أو [NotMapped] لو في C# فقط

5) Multivalued Attribute (سلايد 16)

القاعدة: جدول منفصل: PK الكيان الأصلي كـ FK + عمود القيمة. والـ PK للجدول الجديد = (FK + القيمة) عادة، لأن نفس الرقم مينفعش يتكرر لنفس الشخص.

CREATE TABLE Students (StudentID INT PRIMARY KEY, Name NVARCHAR(100) NOT NULL);
CREATE TABLE StudentPhones (
    StudentID INT          NOT NULL REFERENCES Students(StudentID) ON DELETE CASCADE,
    PhoneNo   NVARCHAR(20) NOT NULL,
    PRIMARY KEY (StudentID, PhoneNo));

SELECT s.StudentID, s.Name, STRING_AGG(p.PhoneNo, ', ') AS Phones          -- SQL Server 2017+
FROM Students s LEFT JOIN StudentPhones p ON p.StudentID = s.StudentID
GROUP BY s.StudentID, s.Name;

modelBuilder.Entity<Student>().OwnsMany(s => s.Phones, p => { p.ToTable("StudentPhones"); p.HasKey("StudentID","PhoneNo"); });

البدائل ومتى تتنازل: (1) عمود JSON (NVARCHAR(MAX) أو ToJson() في EF Core 7+): أسهل في القراءة والكتابة، لكن بلا FK ولا constraints، وبحثه أبطأ. مناسب لو بيانات للعرض فقط. (2) "010,011" في عمود واحد: ممنوع (مفيش integrity ولا index). (3) أعمدة Phone1, Phone2, Phone3: بتحدد سقف وبتكسر الاستعلام لما يظهر الرقم الرابع.

6) Complex Attribute (سلايد 17 و 18)

القاعدة (السلايد): جدول منفصل، وأعمدته: PK الكيان + أجزاء الـ composite، والـ PK = كل ده مع بعض. مثال: PERSON_ADDRESS(PersonID, Street, City, ZIP).

-- حسب السلايد
CREATE TABLE PersonAddress (PersonID INT NOT NULL REFERENCES Persons(PersonID),
    Street NVARCHAR(100) NOT NULL, City NVARCHAR(60) NOT NULL, ZIP NVARCHAR(10) NOT NULL,
    PRIMARY KEY (PersonID, Street, City, ZIP));

نقد التصميم: PK من 4 أعمدة نصية: ثقيل في الـ index، وأي تصحيح في عنوان (Street) = تعديل في PK ولو في جداول بتشاور عليه يتكسر. وكمان بيسمح بنفس العنوان لنفس الشخص بصيغة مختلفة قليلاً. الأفضل في الواقع: surrogate key + قيد على "العنوان الحالي".

CREATE TABLE PersonAddresses (
    AddressID INT IDENTITY PRIMARY KEY,
    PersonID  INT NOT NULL REFERENCES Persons(PersonID),
    Street NVARCHAR(100) NOT NULL, City NVARCHAR(60) NOT NULL, ZIP NVARCHAR(10) NOT NULL,
    IsCurrent BIT NOT NULL DEFAULT 0, ValidFrom DATE NOT NULL, ValidTo DATE NULL);
CREATE UNIQUE INDEX UX_Person_CurrentAddress ON PersonAddresses(PersonID) WHERE IsCurrent = 1;   -- عنوان حالي واحد فقط

ب) أسئلة

  1. ليه ما نخزنش Age؟ وإيه استثناء ممكن؟
  2. جدول StudentPhones بدون PK، ما المشكلة؟
  3. تفتكر تعمل Address كعمود واحد نصي ولا composite؟ ومتى تعمله كيان؟
  4. جدول اسمه Order بيدي error. ليه؟
  5. إيه الفرق بين composite و complex attribute في التحويل؟
الإجابات

(4) لأنها بتتقادم وتتضارب مع BirthDate. الاستثناء: لقطة تاريخية في وقت معين (سن وقت الطلب) تتخزن مقصودة. (5) نفس الرقم ممكن يتكرر لنفس الطالب وبلا integrity، فلازم PK مركب (StudentID, PhoneNo). (6) composite لو عنوان واحد بحث بأجزاءه، وكيان لو عدة عناوين أو تاريخ أو استخدامات (شحن/فوترة). (7) Order كلمة محجوزة، استخدم Orders أو [Order]. (8) composite → أعمدة في نفس الجدول؛ complex (composite + multi-valued) → جدول منفصل بأعمدة الأجزاء.
