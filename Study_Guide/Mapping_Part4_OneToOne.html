1) فكرة الـ 1:1 وقاعدة القرار

في الجدول، علاقة 1:1 معناها: الـ FK لازم يكون UNIQUE (وإلا هتتحول لـ 1:N). والسؤال: الـ FK في أنهي جدول؟ والـ participation هو اللي يرد:

ملحوظة عن التدوين (min,max): سلايدات 31 و 36 بتكتب (0,1) و (1,1) جنب الكيانين. فيه مدرستين: "Look here" (الرقم جنب الكيان يوصف مشاركته هو) و"Look across" (الرقم يوصف الكيان اللي في الطرف التاني). السلايد بيستخدم Look here. وفي Crow's Foot (الأشهر في الأدوات) العكس. اتأكد دايماً من الاتجاه قبل الحكم.

2) إجبارية من الطرفين: DOCTOR و MEDICAL_LICENSE (سلايد 25 إلى 30)

السيناريو: كل دكتور له رخصة طبية واحدة بالظبط، وكل رخصة لدكتور واحد بالظبط.

الخيار A (الـ FK في DOCTOR):

CREATE TABLE MedicalLicenses (
    LicenseID INT PRIMARY KEY, LicenseNumber NVARCHAR(30) NOT NULL UNIQUE,
    IssueDate DATE NOT NULL, ExpiryDate DATE NOT NULL);

CREATE TABLE Doctors (
    DoctorID INT PRIMARY KEY, FullName NVARCHAR(100) NOT NULL, Specialization NVARCHAR(60) NOT NULL, HireDate DATE NOT NULL,
    LicenseID INT NOT NULL UNIQUE                       -- NOT NULL: كل دكتور له رخصة، UNIQUE: رخصة لدكتور واحد
        CONSTRAINT FK_Doctors_Licenses REFERENCES MedicalLicenses(LicenseID));

الخيار B (الـ FK في MEDICAL_LICENSE): نفس الفكرة مع DoctorID INT NOT NULL UNIQUE في الرخصة.

ليه NOT NULL و UNIQUE بالذات؟ (سلايد 28)

INSERT INTO Doctors (DoctorID, FullName, Specialization, HireDate, LicenseID) VALUES (4, 'Dan', 'ENT', '2024-01-01', NULL);   -- ✗ NOT NULL: دكتور بلا رخصة
INSERT INTO Doctors (DoctorID, FullName, Specialization, HireDate, LicenseID) VALUES (5, 'Eve', 'ENT', '2024-01-01', 101);    -- ✗ UNIQUE: الرخصة 101 مرتبطة بدكتور تاني

تصحيح لسلايد 27 و 30: السلايد بيقول إن الخيارين A و B "بيطبقوا mandatory 1:1". الحقيقة: الـ FK مع NOT NULL و UNIQUE بيضمن فقط إن الجدول اللي فيه الـ FK كل صف فيه مرتبط بـ واحد بالظبط من الآخر، لكنه لا يضمن إن كل صف في الجدول التاني له ارتباط. في الخيار A ممكن تضيف رخصة (MedicalLicenses) ومحدش يشاور عليها (رخصة بلا دكتور) والـ DBMS مش هيعترض، رغم إن "كل رخصة لدكتور" total. نفس المشكلة في الخيار B بالعكس.

حلول فعلية للـ total على الطرفين

  1. دمج الجدولين في واحد (الأنظف): لو الاتنين دايماً مع بعض ومفيش سبب للفصل، اعمل Doctors فيها أعمدة الرخصة (LicenseNumber, IssueDate, ExpiryDate).
  2. Shared PK: MedicalLicenses.DoctorID هو PK وFK في نفس الوقت (القسم 5).
  3. Transaction + trigger/منطق تطبيق: تضيف الاتنين في transaction واحدة، وtrigger يرفض الرخصة اليتيمة.
  4. Deferrable constraints: في PostgreSQL، لكن مش في SQL Server.

3) إجبارية من طرف واختيارية من الآخر: FACULTY_MEMBER و OFFICE (سلايد 31 إلى 35)

السيناريو: عضو هيئة التدريس ممكن يكون له مكتب أو لا (0,1)، لكن كل مكتب لازم يخص عضو واحد بالظبط (1,1).

القاعدة: الـ FK في جدول الجانب الـ Total (OFFICE) مع NOT NULL UNIQUE، والجانب الاختياري ما بيحملش حاجة.

CREATE TABLE FacultyMembers (MemberID INT PRIMARY KEY, FullName NVARCHAR(100) NOT NULL, Email NVARCHAR(256) NOT NULL, Department NVARCHAR(80) NOT NULL);
CREATE TABLE Offices (
    OfficeID INT PRIMARY KEY, Building NVARCHAR(60) NOT NULL, RoomNumber NVARCHAR(10) NOT NULL, Phone NVARCHAR(20) NULL,
    MemberID INT NOT NULL UNIQUE REFERENCES FacultyMembers(MemberID));

ليه ده التصميم الأمثل؟

  • لو حطينا OfficeID في FacultyMembers، كل عضو بلا مكتب (member 4 في السلايد 35) هيبقى فيه NULL، وكمان UNIQUE على nullable بيتصرف مختلف (القسم 4).
  • بوضعه في OFFICE الـ total، بنطبق "كل مكتب لعضو" تصريحاً (NOT NULL)، ومفيش NULL في أي حتة.
  • "المكتب لازم يخص عضو" مفروض بالـ DB. "كل عضو له مكتب" غير مطلوب فمش مفروض.
-- أعضاء بلا مكتب (member 4)
SELECT f.MemberID, f.FullName FROM FacultyMembers f LEFT JOIN Offices o ON o.MemberID = f.MemberID WHERE o.OfficeID IS NULL;
-- مكتبين لنفس العضو → ✗ UNIQUE violation
// EF Core: نحدد الـ dependent صراحة في 1:1
modelBuilder.Entity<FacultyMember>().HasOne(f => f.Office).WithOne(o => o.Member)
    .HasForeignKey<Office>(o => o.MemberID).IsRequired();      // EF بينشئ unique index على MemberID تلقائياً

4) اختيارية من الطرفين: STUDENT و LOCKER (سلايد 36 إلى 39)

السيناريو: طالب ممكن يكون له locker أو لا، وlocker ممكن يتخصص لطالب أو لا (0,1)-(0,1).

الخيار 1: جدول علاقة (سلايد 37 إلى 39)

CREATE TABLE StudentLockers (
    StudentID INT NOT NULL PRIMARY KEY REFERENCES Students(StudentID),    -- PK: طالب واحد في صف واحد
    LockerID  INT NOT NULL UNIQUE      REFERENCES Lockers(LockerID),      -- locker واحد لطالب واحد
    AssignedOn DATE NOT NULL DEFAULT CAST(GETDATE() AS DATE));            -- ميزة: خصائص العلاقة

لو طالب معاهوش locker ما فيش صف. الـ NULLs اختفت. وفي السلايد 39 ثلاث حالات: طالب 2 بلا locker، وlocker 102 و 104 غير مخصصين.

الخيار 2: FK nullable في أحد الجدولين (أبسط وأسرع في القراءة)

ALTER TABLE Students ADD LockerID INT NULL REFERENCES Lockers(LockerID);
-- محتاج UNIQUE لكن القيم NULL كتير:
CREATE UNIQUE INDEX UX_Students_Locker ON Students(LockerID) WHERE LockerID IS NOT NULL;   -- filtered unique

أخطر فخ في الـ 1:1 الاختياري: UNIQUE constraint عادي على عمود nullable في SQL Server بيسمح بـ NULL واحد فقط! أول طالب بلا locker تمام، تاني طالب بلا locker → خطأ duplicate. بينما PostgreSQL و MySQL بيسمحوا بأكتر من NULL. الحل في SQL Server: filtered unique index كالمثال. وEF Core غالباً بيضيف الفلتر ده تلقائياً لما تعرّف unique index على عمود nullable في SQL Server (اتأكد من الـ migration الناتج).

رأيي العملي: السلايد بيقترح جدول العلاقة كـ "Recommended for clarity"، وهو مقبول، لكن كتير من المشاريع بتختار FK nullable + filtered unique لأنه أبسط. القرار بيعتمد على: هل العلاقة ليها خصائص؟ ومدى ندرتها؟ وحساسية القراءة؟

modelBuilder.Entity<Student>().HasOne(s => s.Locker).WithOne(l => l.Student)
    .HasForeignKey<Student>(s => s.LockerID).IsRequired(false);

5) Shared Primary Key (PK = FK)

للـ 1:1 اللي فيه جدول "امتداد" (extension) لجدول رئيسي: الـ PK للجدول التابع هو نفسه الـ FK.

CREATE TABLE Users (UserID INT IDENTITY PRIMARY KEY, Email NVARCHAR(256) NOT NULL UNIQUE);
CREATE TABLE UserProfiles (
    UserID INT PRIMARY KEY REFERENCES Users(UserID) ON DELETE CASCADE,    -- PK و FK معاً
    Bio NVARCHAR(500), AvatarUrl NVARCHAR(300), BirthDate DATE);

modelBuilder.Entity<User>().HasOne(u => u.Profile).WithOne(p => p.User).HasForeignKey<UserProfile>(p => p.UserID);
  • مميزاته: الـ 1:1 مضمونة (PK بالتعريف unique)، ومفيش عمود زيادة ولا index زيادة، والـ join على PK سريع.
  • إمتى تفصل جدول من الأصل؟ (1) أعمدة كبيرة أو نادرة الاستخدام (BLOB، bio طويل). (2) صلاحيات مختلفة (بيانات حساسة). (3) معدل تحديث مختلف. (4) الأعمدة اختيارية لمعظم الصفوف (بدل NULLs كتير). وإلا فالدمج أبسط وأسرع.

6) مشاكل الإنتاج في الـ 1:1

  1. NULL في UNIQUE: (القسم 4) أشهر خطأ في SQL Server.
  2. الـ FK في الجانب الغلط: بيعمل NULLs كتير، أو يسمح بـ "رخصة بلا دكتور" بالغلط. القاعدة: الـ FK في جدول الـ Total.
  3. تقسيم بلا سبب: بيضيف join لكل قراءة. اسأل: هل بيتم قراءتهم دايماً مع بعض؟ اندمج.
  4. تبديل التخصيص: تبديل locker بين طالبين بـ UPDATE واحد بيكسر UNIQUE مؤقتاً. استخدم transaction: اجعل الأول NULL، حدّث التاني، ثم الأول.
  5. EF Core: لازم تحدد الـ dependent بـ HasForeignKey<T>، وإلا يخمّن ويطلع خطأ "ambiguous". وانتبه لـ Include (أو projection) لتجنب N+1 عند عرض قائمة.
  6. الحذف: الـ total side بيتحذف مع الأصل (CASCADE) منطقياً، لكن الـ partial side لازم RESTRICT أو SET NULL.

الإجابات

(1) FK في Passports: PersonID INT NOT NULL UNIQUE. (2) جدول علاقة EmployeeParking(EmployeeID PK, SpotID UNIQUE) أو FK nullable في Employees مع filtered unique. (3) Shared PK (Profiles.UserID PK/FK) أو دمج لو مفيش سبب للفصل. (4) دمج في جدول Countries مع CapitalName (لو العاصمة مجرد اسم)، أو جدول Cities لو ليها خصائص والـ FK في Countries (CapitalCityID NOT NULL UNIQUE) لأن الدولة total. (5) UNIQUE في SQL Server بيسمح بـ NULL واحد؛ الحل filtered unique index WHERE LockerID IS NOT NULL. (6) FK في Departments: ManagerID INT NOT NULL UNIQUE REFERENCES Employees(EmployeeID) (القسم total، الموظف partial).
