1) الـ Entity (سلايد 16 إلى 18)

التعريف: كيان من العالم الحقيقي (شخص، شيء، حدث، مفهوم) ليه وجود مستقل ومميّز عن غيره، ومحتاجين نخزن عنه بيانات. بيتمثل بمستطيل واسمه مفرد (CUSTOMER مش CUSTOMERS).

ليه الاسم مفرد؟ لأن الكيان بيمثل نوعاً واحداً (العميل كمفهوم)، والاسم الجمع بيخص المجموعة. في تسمية جداول SQL فيه مدرستين (Customer أو Customers). الأهم الاتساق. و EF Core بيسمي الجدول بجمع اسم الـ DbSet (DbSet<Customer> Customers) افتراضياً.

Strong و Weak (مقدمة سلايد 18)

  • Strong: ليه Primary Key خاص يعرّفه (Customer، Product).
  • Weak: مفيهوش key كامل، بيتعرّف بمفتاح مالكه + مفتاح جزئي (OrderItem، Dependent). شرحه التفصيلي في الجزء 5.

أخطاء شائعة في اكتشاف الكيانات

  1. الكيان العملاق (God Entity): جدول Data أو Info فيه 80 عمود لكل حاجة. ده نفس مشكلة الـ anomalies في الجزء 1.
  2. كيان بدون بيانات: لو الكيان مالوش أي خصائص غير الاسم فغالباً هو قيمة (يبقى خاصية أو lookup).
  3. نسيان كيان الحدث: "حجز" أو "دفعة" أو "تسجيل" بتبقى كيانات مهمة (Booking، Payment، Enrollment) لأن ليها تاريخ وحالة وبيانات خاصة بيها.
  4. خلط الكيان بالدور: Teacher و Student وهما أشخاص. الأفضل غالباً Person + role أو جدولين بحسب اختلاف الخصائص.

2) كيان ولا خاصية؟ قاعدة القرار

اسأل 3 أسئلة: (1) هل ليه خصائص خاصة بيه؟ (2) هل ممكن يتكرر أو يرتبط بأكتر من حاجة؟ (3) هل محتاج أبحث أو أصنّف بيه وأحافظ على قيمه موحدة؟ لو الإجابة نعم فهو كيان.

3) الـ Attribute (سلايد 19 و 20)

التعريف: معلومة بتوصف الكيان. بتتمثل ببيضاوي متصل بالكيان بخط. كل خاصية ليها Domain (نطاق القيم المسموحة): Age بين 0 و 150، Email نص بصيغة معينة، Status من قائمة ثابتة. والـ domain هو اللي بيتحول لـ CHECK و data type و NOT NULL.

4) أنواع الـ Attributes (سلايد 21 و 22) مع التحويل والمشاكل

1) Simple (Atomic)

مينفعش يتقسم لأجزاء ذات معنى: Age، Salary، OrderDate. بتتحول لعمود واحد. السؤال الأهم: هل فعلاً بسيط؟ FullName هل هتحتاج تفرز بالاسم الأخير أو تبحث بالأول؟ لو آه اجعله composite (FirstName و LastName). وفي ثقافات كتير الاسم مش بيتقسم بسهولة، فاقرر حسب احتياج النظام.

2) Composite

بيتقسم لأجزاء ليها معنى: Address = Street + City + Zip. في الجدول بتبقى أعمدة منفصلة (مش عمود نص واحد)، لتقدر تفلتر بالمدينة.

public class Customer
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public Address ShippingAddress { get; set; } = new();     // composite
}
[Owned] public class Address { public string Street { get; set; } = ""; public string City { get; set; } = ""; public string Zip { get; set; } = ""; }

// أو بالـ Fluent API:  modelBuilder.Entity<Customer>().OwnsOne(c => c.ShippingAddress);
// النتيجة: أعمدة ShippingAddress_Street و ShippingAddress_City و ShippingAddress_Zip في جدول Customers

3) Multi-valued

بتشيل أكتر من قيمة: Phones، Skills. ممنوع تخزنها في عمود واحد "010,011". التحويل: جدول منفصل بـ FK للكيان.

CREATE TABLE CustomerPhones (
    CustomerId INT NOT NULL REFERENCES Customers(CustomerId) ON DELETE CASCADE,
    Phone      NVARCHAR(20) NOT NULL,
    PRIMARY KEY (CustomerId, Phone)          -- نفس الرقم مينفعش يتكرر لنفس العميل
);

public class Customer { public int Id { get; set; } public List<CustomerPhone> Phones { get; set; } = new(); }
public class CustomerPhone { public int CustomerId { get; set; } public string Phone { get; set; } = ""; }

مشكلة حقيقية: بيانات مخزنة "C#,SQL" بتخليك تعمل WHERE Skills LIKE '%C#%' وده بيلاقي "C#" لكن كمان "F#,C#-script"، ومفيش index يشتغل (leading wildcard). والحل: جدول، أو في SQL Server 2016+ و EF Core 7/8 ممكن تخزن collection كـ JSON column لو القراءة بس ومش بتفلتر عليها كثير. ده trade-off: JSON أسهل في الكتابة لكن أضعف في الـ constraints والـ joins.

4) Derived

قيمتها تتحسب من خاصية تانية: Age من BirthDate، Total من مجموع الـ items. بتتمثل ببيضاوي متقطع. القاعدة: خزّن الأصل (BirthDate) مش المشتق (Age)، لأن Age بتقدم كل يوم وبتبقى غلط.

// في C#: خاصية محسوبة مش بتتخزن
[NotMapped] public int Age => AgeOn(BirthDate, DateOnly.FromDateTime(DateTime.UtcNow));
static int AgeOn(DateOnly birth, DateOnly today)
{
    var age = today.Year - birth.Year;
    if (today < birth.AddYears(age)) age--;      // لسه ما عداش عيد ميلاده السنة دي
    return age;
}

-- فخ SQL: DATEDIFF بتعد "حدود السنين" مش السنين الكاملة
SELECT DATEDIFF(YEAR, '2000-12-31', '2001-01-01');   -- 1 رغم إن الفرق يوم واحد

TotalAmount في ORDER (سلايد 11 و 33): هي مشتقة (مجموع Quantity × UnitPrice). تخزينها بيسرّع التقارير لكنها بتخلق خطر تضارب (الأصناف اتغيرت والمجموع لا). الخيارات: (1) ما تخزنهاش واحسبها بـ SUM، (2) خزّنها وحدّثها في نفس الـ transaction دايماً، (3) computed column/view لو مجموعة داخل نفس الصف. في المقابلات اذكر إنك فاهم التبادل (consistency مقابل سرعة القراءة).

5) Complex (Composite + Multi-valued)

مثال السلايد: PreviousAddresses (أكتر من عنوان، وكل عنوان فيه Street وCity وZip). التحويل: كيان منفصل بخصائص العنوان + FK + مفتاح.

CREATE TABLE CustomerAddresses (
    AddressId  INT IDENTITY PRIMARY KEY,
    CustomerId INT NOT NULL REFERENCES Customers(CustomerId),
    Street NVARCHAR(100), City NVARCHAR(60), Zip NVARCHAR(10),
    IsCurrent BIT NOT NULL DEFAULT 0, ValidFrom DATE, ValidTo DATE
);

6) Key Attribute

خاصية (أو أكتر) بتعرّف الكيان بشكل فريد، وبتتحط تحتها خط. شرحها كامل في الجزء 3.

Optional و Required

كل خاصية إما NOT NULL أو NULL. الـ NULL معناها "غير معروف" مش صفر ولا نص فاضي. وفي C# فعّل <Nullable>enable</Nullable> عشان string? تطابق عمود NULL. كتر الأعمدة الـ NULL في جدول (sparse) علامة إنك محتاج كيان فرعي أو وراثة.

7) تمارين (اضغط لكشف الإجابة)

أ) صنّف الخاصية

  1. FullName لموظف في نظام HR بسيط.
  2. Email المستخدم الوحيد.
  3. PhoneNumbers للعميل.
  4. YearsOfService للموظف.
  5. DeliveryAddress (street, city, zip) في طلب واحد.
  6. Skills للمبرمج.
  7. OrderTotal.
  8. EducationHistory (جهة، سنة، درجة) لكل موظف عدة سجلات.
الإجابات

(1) Simple أو Composite لو محتاج البحث بالجزء. (2) Simple (وكمان Candidate Key لو unique). (3) Multi-valued. (4) Derived من HireDate. (5) Composite. (6) Multi-valued (والأفضل كيان Skill مشترك ومعاه M:N). (7) Derived من الـ items. (8) Complex (composite + multi-valued)، ويتحول لكيان EducationRecord.

ب) كيان ولا خاصية؟

  1. Brand للمنتج في متجر بيفلتر بالبراند ويعرض صفحة لكل براند.
  2. Gender في نظام عيادة.
  3. Course في نظام تسجيل جامعي.
  4. Country في عنوان العميل (200 دولة).
الإجابات

(9) Entity (ليه صفحة وخصائص وهيتكرر). (10) Attribute بقيم محددة (أو lookup صغير). (11) Entity. (12) غالباً Entity/Lookup (Country) لتوحيد الأسماء ومنع الأخطاء الإملائية، أو ISO code كـ attribute لو الاحتياج بسيط.

ج) صمم الخصائص (جرّب بنفسك)

نظام مكتبة: Book و Member. اكتب خصائص كل كيان ونوعها، وحدّد الـ multi-valued والـ derived، وقرر هل Author كيان.

حل مقترح

BOOK: ISBN (key)، Title، PublishYear، Pages، CopiesTotal، AvailableCopies (derived من CopiesTotal - الاستعارات الجارية)، Authors (multi-valued ← كيان AUTHOR مع M:N)، Categories (multi-valued ← كيان). MEMBER: MemberId، Name (composite)، Email، Phones (multi-valued)، JoinDate، Age (derived من BirthDate). Author كيان لأنه ليه سيرة وكتب كتير.

د) اكتشف الخطأ

Orders(OrderId, CustomerName, CustomerPhone1, CustomerPhone2, CustomerPhone3, ItemsList, Age)
الإجابة

(1) CustomerName و CustomerPhone في الطلب: تكرار، المفروض كيان Customer. (2) Phone1 و 2 و 3: multi-valued مقلّد بأعمدة، وبيحدد الحد الأقصى بـ 3. (3) ItemsList: قائمة في عمود، المفروض ORDER_ITEM. (4) Age: مشتقة وغير مرتبطة بالطلب أصلاً.
