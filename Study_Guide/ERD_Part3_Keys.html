ERD (الجزء 3 من 6): الـ Keys بكل أنواعها

سلايدات 23 إلى 26. المفاتيح هي أكتر موضوع بيتسأل فيه في المقابلات وأكتر مكان بتتخذ فيه قرارات بتعيش سنين في المشروع. بنمشي من التعريف للقرار العملي (Natural مقابل Surrogate) وللتطبيق في SQL و EF Core.

1) ليه محتاجين Keys؟ (سلايد 24)

جدول فيه عميلين اسمهم "Ahmed Ali": مين فيهم اللي اشترى؟ من غير حاجة تميّز كل صف بشكل مضمون، مفيش طريقة تحدد صف بعينه للتعديل أو الحذف أو الربط. الـ Key هو خاصية (أو مجموعة خصائص) قيمتها فريدة لكل instance فبتعرّفه بدون لبس.

UPDATE Customers SET Phone = '0102' WHERE Name = 'Ahmed Ali';      -- عدّل عميلين!
UPDATE Customers SET Phone = '0102' WHERE CustomerId = 1;          -- عدّل واحد بالظبط

والـ keys كمان هي الأساس اللي بنربط بيه الجداول (Foreign Keys)، فبدونها مفيش علاقات.

2) الأنواع وعلاقتها ببعض (سلايد 25 و 26)

النوعالتعريف الدقيقمثال (EMPLOYEE)
Super Keyأي مجموعة خصائص تضمن التفرّد، وممكن يكون فيها خصائص زيادة{EmpID}، {EmpID, Name}، {Email, Phone}
Candidate KeySuper Key minimal: لو شلت أي خاصية منها تفقد التفرّد{EmpID}، {Email}، {NationalID}
Primary Keyالـ Candidate اللي اخترته ليعرّف الكيان (واحد فقط، NOT NULL)EmpID
Alternate Keyباقي الـ Candidates اللي ما اتختارتش (بتتنفذ UNIQUE)Email، NationalID
Composite KeyKey من خاصيتين أو أكتر مع بعض(OrderID, ProductID)
Foreign Keyخاصية تشاور على Key (PK أو Unique) في كيان آخر وتحقق الـ referential integrityORDER_ITEM.OrderID يشاور على ORDER.OrderID

أخطاء المفاهيم الأشهر:

  1. "Super Key هو الـ Primary Key": لأ، الـ PK نوع واحد مختار من اللي بعده.
  2. "كل Super Key هو Candidate": لأ، Candidate لازم يكون minimal. {EmpID, Name} Super لكن مش Candidate لأن {EmpID} كفاية.
  3. "الـ Key بيتحدد بالنظر للبيانات الموجودة": لأ، المفتاح قاعدة عمل (property of the schema)، مش ملاحظة على الصفوف الحالية. لو الأرقام الحالية فريدة بالصدفة فمش معناه إنها Key.
  4. "الـ Foreign Key لازم يشاور على PK": القاعدة العامة إنه يشاور على أي Candidate (unique) وفي SQL Server لازم PK أو UNIQUE constraint.

3) مثال تفصيلي: إزاي تطلّع الـ Keys

  1. اسأل بقواعد العمل: إيه الخصائص اللي مضمون إنها فريدة لكل موظف؟ EmpID (نظامنا بيولدها)، NationalID (رقم قومي واحد لكل شخص)، Email (بنفرضه unique). Name لأ (الصف 1 و 2). Phone ممكن يتشارك (مكتب).
  2. Candidate Keys: {EmpID}، {NationalID}، {Email}. وأي مجموعة فيها واحدة منهم + أي حاجة تانية هي Super مش Candidate.
  3. Primary Key: EmpID (سبب الاختيار في القسم 4). Alternate: NationalID و Email.
  4. عدد الـ Super Keys: الجدول فيه 5 خصائص. أي مجموعة فيها EmpID هي Super: 2⁴ = 16. نفس الشيء لـ NationalID (16) ولـ Email (16)، وبنطرح المتكرر (اللي فيها أكتر من واحد). فالعدد الكلي أكبر من 16 وده سبب إننا بنشتغل بالـ Candidate (الأصغر) مش بالـ Super.
CREATE TABLE Employees (
    EmpID      INT IDENTITY(1,1) PRIMARY KEY,           -- Primary
    NationalID CHAR(14)      NOT NULL UNIQUE,           -- Alternate
    Email      NVARCHAR(256) NOT NULL UNIQUE,           -- Alternate
    Name       NVARCHAR(100) NOT NULL,
    Phone      NVARCHAR(20)  NULL
);

4) الـ Primary Key: خصائصه وقرار الاختيار

الـ PK الجيد: Unique و NOT NULL و Stable (ما بيتغيرش) و Minimal (أقل عدد أعمدة) و Simple (نوع صغير وسريع المقارنة).

مشاكل حقيقية في الإنتاج

  1. الإيميل PK: العميل غيّر إيميله فلازم تعدّل كل الجداول اللي بتشاور عليه، أو تفقد الربط.
  2. أرقام تسلسلية في الـ URL: /orders/1042 بتخلي أي مستخدم يجرب 1043 (IDOR/enumeration). الحل: تحقق من الصلاحية دايماً، وممكن تعرض معرّف عام (GUID) منفصل عن الـ PK الداخلي.
  3. GUID عشوائي كـ clustered PK: كل insert بيروح لمكان عشوائي في الـ index فبتتشقق الصفحات (page splits) ويكبر حجم الـ index ويبطّأ. الحل: GUID متسلسل (NEWSEQUENTIALID() أو Guid.CreateVersion7() في .NET 9 فما فوق، راجع التوثيق) أو BIGINT.
  4. INT بيخلص: الحد حوالي 2.1 مليار. جداول الـ logs والـ events الكبيرة محتاجة BIGINT من الأول لأن تغيير نوع PK بعدين مؤلم.
  5. فجوات في الـ IDENTITY: rollback أو restart بيسيب فجوات. الـ PK مش مفروض يكون "رقم متسلسل بلا فجوات" للمحاسبة، لو محتاج ترقيم فواتير بلا فجوات استخدم عمود مستقل بمنطق خاص.

5) Composite Key (سلايد 26)

لما التفرّد بييجي من اتحاد خاصيتين، زي (OrderID, ProductID) في ORDER_ITEM: الطلب الواحد ممكن يحتوي منتجات كتير، والمنتج في طلبات كتير، لكن التركيبة مرة واحدة.

CREATE TABLE OrderItems (
    OrderID   INT NOT NULL REFERENCES Orders(OrderID),
    ProductID INT NOT NULL REFERENCES Products(ProductID),
    Quantity  INT NOT NULL CHECK (Quantity > 0),
    UnitPrice DECIMAL(10,2) NOT NULL,
    PRIMARY KEY (OrderID, ProductID)
);
Composite PKSurrogate PK + Unique على التركيبة
يمنع التكرار تلقائياً ومفيش عمود زيادةعمود Id بسيط ويسهّل الـ FK من جداول تانية
أي جدول ابن لازم ينقل أعمدة المفتاح كلهاFK بعمود واحد
EF Core: HasKey(x => new { x.OrderID, x.ProductID })أبسط في الـ API (/items/5)

فخ واقعي: لو العميل يقدر يضيف نفس المنتج مرتين كسطرين منفصلين (بأسعار أو ملاحظات مختلفة)، المفتاح (OrderID, ProductID) هيرفض. محتاج ساعتها LineNo كجزء من المفتاح، أو surrogate key. ودي فكرة "المفتاح الجزئي" في الـ weak entity (الجزء 5). كمان ترتيب الأعمدة في الـ composite index مهم: (OrderID, ProductID) يخدم البحث بـ OrderID لكن مش بـ ProductID لوحده.

6) الـ Foreign Key والـ Referential Integrity

الـ FK قاعدة بتقول: "القيمة دي لازم تكون موجودة في الجدول التاني (أو NULL لو مسموح)". وبتحمي من الـ orphan rows:

-- من غير FK
DELETE FROM Customers WHERE CustomerID = 1;     -- الطلبات لسه بتشاور على عميل مش موجود → تقارير غلط

-- مع FK
ALTER TABLE Orders ADD CONSTRAINT FK_Orders_Customers
    FOREIGN KEY (CustomerID) REFERENCES Customers(CustomerID) ON DELETE NO ACTION;
-- الحذف بيفشل طالما فيه طلبات (قرار واعي)
ON DELETEبيعمل إيهإمتى
NO ACTION / RESTRICTيرفض الحذف لو فيه أبناءالافتراضي الآمن، لعميل عنده طلبات
CASCADEيحذف الأبناء معاهأبناء ملهمش معنى لوحدهم (OrderItems مع Order)
SET NULLيخلي FK = NULLعلاقة اختيارية (مدير اتحذف)

مشاكل واقعية: (1) CASCADE على علاقة غلط ممكن يمسح بيانات مهمة بحذف واحد، وSQL Server بيرفض تعدد مسارات الـ cascade وبيطلب تحدد يدوياً. (2) SQL Server ما بيعملش index تلقائي على أعمدة الـ FK، فالـ join والحذف على الجدول الأب بيعملوا scan لو نسيت index (EF Core بيضيفه تلقائياً). (3) FK يقبل NULL = علاقة اختيارية (partial participation). FK مع NOT NULL = إجبارية (total).

Soft delete: في الأنظمة المالية غالباً ما بنحذفش فعلياً، بنستخدم IsDeleted أو DeletedAt. وده معناه أي unique constraint لازم يراعي ده (filtered index) وإلا مش هتقدر تعيد استخدام نفس الإيميل.

7) الـ Keys في رسم الـ ERD

  • الـ key attribute بيتحط تحته خط (سلايد 24). والـ composite key: كل الخصائص المشتركة فيه تحتها خط.
  • الـ partial key (في weak entity) خط متقطع.
  • في Crow's Foot بيتكتب PK و FK جنب العمود (زي سلايد 14).

ملاحظة على السلايدات: سلايد 14 بيعرض FK كمكوّن في الـ ERD. في Chen الكلاسيكي الـ FK مش بيتحط كخاصية، العلاقة (المعين) هي اللي بتعبّر عن الارتباط، والـ FK بيظهر لما تحول الـ ERD للـ logical schema. أما في Crow's Foot/أدوات التصميم فبتشوفه كعمود. الاتنين صح بحسب مستوى الرسم.

8) التطبيق في EF Core

public class Employee
{
    public int EmpID { get; set; }                       // Primary (اتفاقية Id أو ClassNameId)
    public string NationalID { get; set; } = "";
    public string Email { get; set; } = "";
    public List<OrderItem> Items { get; set; } = new();
}

modelBuilder.Entity<Employee>(e =>
{
    e.HasKey(x => x.EmpID);
    e.HasAlternateKey(x => x.NationalID);               // Alternate: unique + ممكن تكون Principal Key لـ FK
    e.HasIndex(x => x.Email).IsUnique();                // unique عادي
});

modelBuilder.Entity<OrderItem>(i =>
{
    i.HasKey(x => new { x.OrderID, x.ProductID });       // Composite
    i.HasOne(x => x.Order).WithMany(o => o.Items).HasForeignKey(x => x.OrderID)
     .OnDelete(DeleteBehavior.Cascade);
    i.HasOne(x => x.Product).WithMany().HasForeignKey(x => x.ProductID)
     .OnDelete(DeleteBehavior.Restrict);                // مينفعش تمسح منتج اتباع
});

9) تمارين (اضغط لكشف الإجابة)

  1. جدول Student(ID, NatID, Email, Name, Phone) وكلهم فريدين ما عدا Name و Phone. اكتب Candidate Keys وPK واحد من عندك وAlternate Keys.
  2. هل {ID, Name} Candidate Key؟ ولو لأ ليه، وهل هو Super Key؟
  3. جدول Enrollment(StudentID, CourseID, Semester, Grade): الطالب ياخد نفس الكورس في ترم مختلف لو رسب. إيه الـ PK؟
  4. مبرمج اختار الإيميل كـ PK لجدول Users. إيه 3 مشاكل متوقعة؟
  5. عدد الـ Super Keys في R(A,B,C) لو A هو الـ Candidate الوحيد؟
  6. موقع بيعرض /invoice/5001 لكل فاتورة. إيه المخاطرة؟ وإيه الحل؟
  7. FK في جدول Orders على ManagerID لموظف قد يكون مفيش، هل NOT NULL؟
  8. جدول OrderItems له PK (OrderID, ProductID) ومحتاجين نسمح بنفس المنتج مرتين. عدّل التصميم.
الإجابات

(1) Candidates: {ID}، {NatID}، {Email}. PK = ID (الأصغر والأثبت). Alternate = NatID و Email. (2) لأ، مش minimal لأن {ID} لوحدها كفاية، لكنها Super Key. (3) (StudentID, CourseID, Semester) لأن الـ Semester جزء من التفرّد. (4) الإيميل بيتغير وده يكسر FKs، حجمه كبير فيبطّأ الـ joins، ومعلومة حساسة بتتسرب في كل جدول ابن. (5) 4: {A}، {A,B}، {A,C}، {A,B,C}. (6) enumeration/IDOR: أي حد يجرب أرقام. الحل: تحقق صلاحية المالك، ومعرّف عام (GUID) للعرض. (7) لأ، nullable (علاقة اختيارية = partial participation). (8) أضف LineNo: PK = (OrderID, LineNo) مع UNIQUE اختياري على التركيبة لو بدك تمنعه في حالات أخرى، أو surrogate OrderItemID.
