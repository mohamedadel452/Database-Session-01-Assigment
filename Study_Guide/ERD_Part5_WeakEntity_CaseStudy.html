ERD (الجزء 5 من 6): Weak Entity ومثال تصميم كامل

سلايدات 41 إلى 46. الـ Weak Entity أكتر موضوع بيتلخبط فيه الطلبة، وفيه خطأ رسم في سلايد 43 لازم تعرفه. وبعده مثال متجر إلكتروني كامل من الـ ERD للـ SQL والـ EF Core، وخطوات منهجية لتصميم أي ERD.

1) إيه هو الـ Weak Entity؟ (سلايد 41 و 42)

الفكرة: كيان مفيهوش مفتاح كامل يميّزه لوحده. هويته بتعتمد على كيان تاني (الـ Owner / Identifying / Strong Entity). مثال: الـ DEPENDENT (تابع الموظف). الاسم "Mona" لوحده مش بيميّز (ممكن موظفين كتير عندهم تابع اسمه Mona). لكن (EmpID + DepName) بيميّزه.

صيغة المفتاح: Primary Key الـ Weak = (PK الـ Owner) + (Partial Key / Discriminator)

ليه الفكرة موجودة؟

لأن في الواقع في أشياء ملهاش معنى بدون أصلها: بند طلب من غير طلب، فصل من غير كتاب، تابع من غير موظف. الـ weak entity بيعبّر عن ده في النموذج وبيفرض إن ما فيش instance يعيش من غير مالكه.

Weak مقابل Dependent (دقة مهمة)

في التعريف الصارم، Weak = identification-dependent (مفتاحه بيتكوّن من مفتاح المالك). لكن ممكن كيان يكون existence-dependent فقط (يموت بموت المالك) وفي نفس الوقت له surrogate key خاص فيه، وساعتها في التصميم العملي بيتعامل كـ strong entity عادي مع FK NOT NULL و ON DELETE CASCADE. ودي القرارات اللي بتتاخد فعلياً في معظم الأنظمة.

تصحيح رسم سلايد 43: السلايد بيرسم الخط المزدوج بين EMPLOYEE والمعين HAS_DEPENDENT، وخط مفرد ناحية DEPENDENT. بينما الشرح تحته بيقول "total participation of DEPENDENT". الرسم عكس القاعدة: الخط المزدوج لازم يكون على جنب الـ Weak (DEPENDENT)، لأن كل تابع لازم يكون له موظف، والموظف ممكن يكون من غير توابع (partial). كمان ناقص كتابة الـ cardinality: 1 عند EMPLOYEE و N عند DEPENDENT. ومصادر زي كتاب Bagui & Earp وCreately بتأكد إن الـ weak entity دايماً مشاركته total.

ملاحظة تصميمية على نفس السلايد: EMPLOYEE فيها خاصية Department كنص. في تصميم حقيقي Department كيان مستقل (الجزء 2) ومعاه علاقة 1:N، وإلا كل ما اسم قسم يتغير هتعدل مئات الصفوف.

3) خصائص الـ Weak Entity (سلايد 44)

  1. ملوش Primary Key بنفسه.
  2. وجوده معتمد على المالك (حذف المالك = حذف الـ weak، عبر CASCADE).
  3. مشاركته في العلاقة المعرِّفة total دايماً.
  4. مفتاحه = مفتاح المالك + partial key.
  5. العلاقة المعرِّفة بتكون 1:N (مالك واحد، weak كتير). مش M:N لأن الـ weak لازم ليه مالك واحد يعرّفه.
  6. الـ partial key لازم يكون فريد داخل نفس المالك فقط، مش في الجدول كله.

ORDER_ITEM بيلعب دورين: (1) weak entity على ORDER (هويته = OrderID + ItemNo)، و(2) كيان ربط (associative) بين ORDER و PRODUCT بخصائصه (Quantity و UnitPrice). عشان كده في الجزء 3 ناقشنا اختيار PK بين (OrderID, ProductID) و (OrderID, LineNo). الثاني أمرن (يسمح بنفس المنتج مرتين) والأول يمنع التكرار.

5) التحويل لجداول (سلايد 46)

  1. اعمل جدول للـ Owner بـ PK عادي.
  2. اعمل جدول للـ Weak.
  3. أضف PK الـ Owner في جدول الـ Weak كـ Foreign Key.
  4. PK الـ Weak = (FK الـ Owner + Partial Key).
CREATE TABLE Employees (
    EmpID INT PRIMARY KEY, EmpName NVARCHAR(100) NOT NULL, HireDate DATE NOT NULL);

CREATE TABLE Dependents (
    EmpID        INT          NOT NULL,                       -- FK + جزء من PK
    DepName      NVARCHAR(60) NOT NULL,                       -- partial key
    BirthDate    DATE         NULL,
    Gender       CHAR(1)      NULL,
    Relationship NVARCHAR(30) NOT NULL,
    PRIMARY KEY (EmpID, DepName),
    FOREIGN KEY (EmpID) REFERENCES Employees(EmpID) ON DELETE CASCADE   -- حذف الموظف = حذف توابعه
);

EF Core: طريقتين

// 1) كيان عادي بمفتاح مركب
modelBuilder.Entity<Dependent>(d =>
{
    d.HasKey(x => new { x.EmpID, x.DepName });
    d.HasOne(x => x.Employee).WithMany(e => e.Dependents).HasForeignKey(x => x.EmpID).OnDelete(DeleteBehavior.Cascade);
});

// 2) Owned collection: بيمثّل existence + identification dependence طبيعياً
modelBuilder.Entity<Employee>().OwnsMany(e => e.Dependents, d =>
{
    d.WithOwner().HasForeignKey("EmpID");
    d.Property<int>("Id");  d.HasKey("Id");               // أو HasKey("EmpID","DepName")
    d.ToTable("Dependents");
});

الـ Owned types معناها إنك مش هتعمل db.Dependents مباشرة، بتتعامل معاهم عن طريق الـ Employee. مناسبة لما الـ weak entity بتتعامل معاه دايماً مع مالكه.

مشاكل واقعية: (1) أي جدول ابن للـ weak (مثلاً DependentMedicalRecords) لازم يكرر مفتاحه المركب كله (EmpID, DepName). فكتير بيضيفوا surrogate key للـ weak (DependentId IDENTITY) مع UNIQUE (EmpID, DepName) وده يحافظ على القاعدة ويسهّل الـ FKs. (2) لو الـ partial key اتغيّر (تصحيح اسم) فبيتحدّث PK وكل FKs اللي بتشاور عليه. (3) توأم بنفس الاسم تحت نفس الموظف: القيد بيرفض. لازم partial key أفضل (DependentNo).

6) مثال كامل: متجر إلكتروني (من الفكرة للـ SQL و EF Core)

المتطلبات: العميل بيعمل طلبات (ممكن عميل جديد من غير طلبات)، كل طلب لازم لعميل. الطلب فيه بنود، كل بند لمنتج واحد بكمية وسعر وقت الشراء. المنتج في فئة واحدة، والفئة فيها منتجات كتير.

CREATE TABLE Customers  (CustomerID INT IDENTITY PRIMARY KEY, Name NVARCHAR(100) NOT NULL,
                         Email NVARCHAR(256) NOT NULL UNIQUE, Phone NVARCHAR(20));
CREATE TABLE Categories (CategoryID INT IDENTITY PRIMARY KEY, Name NVARCHAR(80) NOT NULL UNIQUE);
CREATE TABLE Products   (ProductID INT IDENTITY PRIMARY KEY, Name NVARCHAR(150) NOT NULL,
                         UnitPrice DECIMAL(10,2) NOT NULL CHECK (UnitPrice >= 0), Stock INT NOT NULL DEFAULT 0 CHECK (Stock >= 0),
                         CategoryID INT NOT NULL REFERENCES Categories(CategoryID));
CREATE TABLE Orders     (OrderID INT IDENTITY PRIMARY KEY, OrderDate DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
                         CustomerID INT NOT NULL REFERENCES Customers(CustomerID));           -- total (NOT NULL)
CREATE TABLE OrderItems (OrderID INT NOT NULL REFERENCES Orders(OrderID) ON DELETE CASCADE,   -- weak entity
                         LineNo INT NOT NULL,
                         ProductID INT NOT NULL REFERENCES Products(ProductID),
                         Quantity INT NOT NULL CHECK (Quantity > 0),
                         UnitPrice DECIMAL(10,2) NOT NULL,                                   -- سعر وقت الشراء
                         PRIMARY KEY (OrderID, LineNo));
CREATE INDEX IX_Orders_Customer ON Orders(CustomerID);
CREATE INDEX IX_OrderItems_Product ON OrderItems(ProductID);
public class Order { public int OrderID { get; set; } public DateTime OrderDate { get; set; }
    public int CustomerID { get; set; } public Customer Customer { get; set; } = null!; public List<OrderItem> Items { get; set; } = new(); }
public class OrderItem { public int OrderID { get; set; } public int LineNo { get; set; } public int ProductID { get; set; }
    public int Quantity { get; set; } public decimal UnitPrice { get; set; } public Order Order { get; set; } = null!; public Product Product { get; set; } = null!; }

modelBuilder.Entity<OrderItem>(i =>
{
    i.HasKey(x => new { x.OrderID, x.LineNo });
    i.HasOne(x => x.Order).WithMany(o => o.Items).HasForeignKey(x => x.OrderID).OnDelete(DeleteBehavior.Cascade);
    i.HasOne(x => x.Product).WithMany().HasForeignKey(x => x.ProductID).OnDelete(DeleteBehavior.Restrict);
    i.Property(x => x.UnitPrice).HasPrecision(10, 2);
});

// إجمالي طلب (derived attribute): اتحسب ولا تخزنه، أو خزّنه وحدّثه في نفس الـ transaction
var total = await db.OrderItems.Where(i => i.OrderID == id).SumAsync(i => i.Quantity * i.UnitPrice);

قرارات المثال: (1) UnitPrice مكرر في OrderItem لأنه snapshot تاريخي. (2) Orders.CustomerID NOT NULL (total للطلب)، والعميل بلا طلبات مسموح (partial). (3) ON DELETE RESTRICT على المنتج حتى ما نفقدش تاريخ المبيعات. (4) الـ index على الـ FKs. (5) التقارير الكبيرة: لو الاستعلام بيجمع ملايين البنود كل مرة، فكر في تخزين Total مع الحفاظ على consistency.

7) خطوات منهجية لتصميم أي ERD (للمشاريع والامتحانات)

  1. اقرأ المتطلبات وحدد الأسماء (candidate entities) والأفعال (relationships).
  2. لكل اسم اسأل: كيان ولا خاصية؟ (القسم 2 في الجزء 2).
  3. حدد الخصائص لكل كيان وأنواعها (simple/composite/multi-valued/derived).
  4. حدد المفاتيح: Candidates ثم PK، وهل في weak entities؟
  5. ارسم العلاقات وحدد الدرجة (binary/ternary/unary).
  6. لكل علاقة: Cardinality من الاتجاهين، ثم Participation من كل جانب.
  7. حلّ الـ M:N بجدول وسيط، وحدد خصائص العلاقة.
  8. حوّل لجداول: FK في جانب الـ N، NOT NULL حسب الـ total.
  9. راجع: anomalies؟ تكرار؟ مفاتيح؟ أسماء متسقة؟ احتياجات الأداء (indexes)؟
  10. اعرضه على أصحاب العمل وعدّله قبل الكتابة.

9) تمارين (اضغط لكشف الإجابة)

  1. أي من دول Weak: (أ) ROOM في BUILDING، (ب) CUSTOMER، (ج) CHAPTER في BOOK، (د) PRODUCT، (هـ) SEAT في FLIGHT؟
  2. اكتب PK لـ COMMENT تحت POST لو الـ CommentNo بيبدأ من 1 لكل بوست.
  3. ليه الـ Dependents ما ينفعش لها علاقة M:N مع Employee في الـ identifying؟
  4. صحّح: "الخط المزدوج عند EMPLOYEE في HAS_DEPENDENT".
  5. مصمم حط OrderItems(OrderID, ProductID) كـ PK. المستخدم ضغط "أضف" مرتين على نفس المنتج بملاحظتين مختلفتين. إيه اللي حصل وإيه الحل؟
  6. صمم weak entity: SEAT داخل THEATER_HALL (مع تحويل لجداول).
الإجابات

(1) أ و ج و هـ. (2) (PostID, CommentNo). (3) لأن الـ weak لازم يتعرّف بمالك واحد، وM:N معناها أكتر من مالك. (4) الخط المزدوج يتحط عند DEPENDENT (الـ weak) لأنه total، وEMPLOYEE بخط مفرد (partial) مع كتابة 1 و N. (5) المفتاح الأساسي بيرفض الإدخال الثاني (violation). الحل: LineNo في المفتاح (OrderID, LineNo) أو دمج الكمية في السطر الأول بمنطق التطبيق. (6) HALL(HallID PK, Name) و SEAT(HallID FK, SeatNo, SeatType, PK(HallID, SeatNo), FK→HALL ON DELETE CASCADE).
