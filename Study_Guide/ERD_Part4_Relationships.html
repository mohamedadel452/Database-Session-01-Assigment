1) الـ Relationship (سلايد 27 إلى 29)

التعريف: ارتباط بين كيانين أو أكتر، بيتمثل بمعين (Diamond) واسمه فعل بيعبّر عن الحدث: STUDENT ENROLLS IN COURSE. الاسم بيتقرأ في اتجاه، وبيتعاكس في الاتجاه التاني (COURSE HAS STUDENTS). لو الكيان بيشارك أكتر من مرة في نفس العلاقة (recursive) بنحط role names: EMPLOYEE (manager) و EMPLOYEE (subordinate).

3) الـ Cardinality (سلايد 31 إلى 35)

التعريف: أقصى عدد من instances الكيان B ممكن يرتبط بـ instance واحد من A (وبالعكس). بيجاوب على "كام؟".

4) الـ Participation (سلايد 36 إلى 40)

التعريف: هل الـ instance لازم يشارك في العلاقة (الحد الأدنى = 1) ولا ممكن (الحد الأدنى = 0)؟ بيجاوب على "لازم ولا اختياري؟".

النوعالرسم (Chen)المعنىفي الجدول
Total (Mandatory)خط مزدوج ═كل instance لازم يشارك (min = 1)FK NOT NULL (في جانب الـ N)
Partial (Optional)خط مفرد ─ممكن يشارك وممكن لأ (min = 0)FK NULL مسموح
  • Total على EMPLOYEE في WORKS_FOR: مفيش موظف بلا قسم (DeptID NOT NULL).
  • Partial على SUPPLIER في SUPPLIES: مورّد ممكن مفيش منتجات عنده لسه.

5) الفرق بين Cardinality و Participation + تصحيح سلايد 38

CardinalityParticipation
بيجاوب علىكام (الحد الأقصى)لازم ولا لأ (الحد الأدنى)
القيم1 أو N0 أو 1 (partial أو total)
الرسمرقم/شوكة غرابخط مزدوج/مفرد أو شرطة/دائرة

تصحيح مهم (سلايد 38): السلايد بيقول: "Every CUSTOMER must place at least one ORDER (Total)" و"An ORDER belongs to one CUSTOMER (Partial)". ده فيه خطأين: (1) جملة "ORDER belongs to one CUSTOMER" بتتكلم عن cardinality (واحد) مش participation. (2) منطقياً الطلب لازم يكون له عميل (total participation لجانب ORDER، يعني CustomerID NOT NULL)، لكن العميل الجديد ممكن مايكونش عمل طلبات لسه (partial لجانب CUSTOMER). السلايد عكسهم.
الصح: CUSTOMER (0..N) ─PLACES─ ORDER (1..1).

ملاحظة هندسية: total participation على جانب الـ "1" (كل عميل لازم له طلب واحد على الأقل) مش بيتحقق بالـ FK لوحده، لأن الطلب لازم يعرف العميل أولاً (مشكلة الدجاجة والبيضة). بتحتاج منطق تطبيق أو trigger أو deferred constraint. أما total على جانب الـ "N" (الطلب لازم له عميل) فهو NOT NULL بسيط.

مثال سلايد 38 التاني: PRODUCT (partial: ممكن ما يتباعش) و ORDER_ITEM (total: كل صنف لازم يكون لمنتج). ده صح تماماً: ProductID NOT NULL في OrderItems.

6) تحويل العلاقات لجداول (القواعد الخمس) مع الكود

1) One-to-Many: FK في جانب الـ N

CREATE TABLE Employees (EmpID INT PRIMARY KEY, Name NVARCHAR(100),
    DeptID INT NOT NULL REFERENCES Departments(DeptID));        -- NOT NULL = total participation

// EF Core
modelBuilder.Entity<Employee>().HasOne(e => e.Department).WithMany(d => d.Employees)
    .HasForeignKey(e => e.DeptID).IsRequired();

2) One-to-One

CREATE TABLE Passports (PassportID INT PRIMARY KEY,
    PersonID INT NOT NULL UNIQUE REFERENCES Persons(PersonID),  -- UNIQUE هو اللي بيجعلها 1:1
    Number NVARCHAR(20));

modelBuilder.Entity<Person>().HasOne(p => p.Passport).WithOne(x => x.Person).HasForeignKey<Passport>(x => x.PersonID);

الـ FK يروح فين؟ في الجدول اللي مشاركته total (الجواز لازم لشخص، والشخص ممكن من غير جواز). وبدائل: ضمّ الجدولين في واحد، أو استخدام نفس الـ PK (shared primary key). وسّع الجدول لجدولين لما: بيانات اختيارية كبيرة (صورة)، أو صلاحيات مختلفة، أو تحديث بوتيرة مختلفة.

3) Many-to-Many: جدول وسيط (Junction / Associative)

CREATE TABLE Enrollments (
    StudentID  INT NOT NULL REFERENCES Students(StudentID),
    CourseID   INT NOT NULL REFERENCES Courses(CourseID),
    Grade      DECIMAL(4,2) NULL,                 -- خاصية العلاقة نفسها!
    EnrolledAt DATE NOT NULL,
    PRIMARY KEY (StudentID, CourseID));

// EF Core: join entity صريح لأن فيه Grade
public class Enrollment { public int StudentID { get; set; } public int CourseID { get; set; }
    public decimal? Grade { get; set; } public Student Student { get; set; } = null!; public Course Course { get; set; } = null!; }
modelBuilder.Entity<Enrollment>().HasKey(e => new { e.StudentID, e.CourseID });
// لو مفيش خصائص للعلاقة: modelBuilder.Entity<Student>().HasMany(s => s.Courses).WithMany(c => c.Students);

4) Recursive: FK للجدول نفسه

CREATE TABLE Employees (EmpID INT PRIMARY KEY, Name NVARCHAR(100),
    ManagerID INT NULL REFERENCES Employees(EmpID));       -- NULL للمدير الأعلى (partial)

7) مشاكل حقيقية متكررة

  1. M:N من غير جدول وسيط: Students.CourseIds = "1,2,3" (مرّ في الجزء 2). مفيش integrity ولا بحث.
  2. الـ FK في الجدول الغلط: Departments.EmployeeID بيسمح لقسم بموظف واحد. اسأل "مين الـ N؟" وحط الـ FK عنده.
  3. الـ 1:1 اللي ملهاش لازمة: تقسيم جدول لـ 2 بدون سبب بيضيف joins. ادمج إلا لو فيه سبب واضح.
  4. نسيان خصائص العلاقة: Grade مش للطالب ولا للكورس، دي للتسجيل. نفس الشيء Quantity في ORDER_ITEM.
  5. M:N المخفية: "الموظف في قسم واحد" لحد ما يظهر موظف بيشتغل في قسمين. اسأل صاحب العمل قبل ما تثبّت 1:N.
  6. التاريخ (Temporal): "الموظف في قسم واحد" لكن عايز تحتفظ بتاريخ النقل: دي بقت EmployeeDepartmentHistory (EmpID, DeptID, From, To).
  7. Cycle في الـ cascade: علاقتين بين نفس الجدولين بـ cascade بيعملوا مسارات متعددة في SQL Server. حدد Restrict في واحدة.

8) تمارين (اضغط لكشف الإجابة)

أ) حدد الـ Cardinality

  1. مستخدم ← الحسابات البنكية (حساب مشترك مسموح).
  2. بلد ← عاصمة.
  3. مؤلف ← كتاب.
  4. طلب ← شحنة (الطلب بيتقسم لشحنات، والشحنة لطلب واحد).
  5. مستخدم ← صورة البروفايل الحالية.
  6. مقال ← وسوم (tags).
الإجابات

(1) M:N (حساب مشترك). (2) 1:1. (3) M:N (مؤلفين مشتركين) أو 1:N لو افترضت مؤلف واحد، والصح تسأل. (4) 1:N. (5) 1:1. (6) M:N عبر جدول ArticleTags.

ب) حدد الـ Participation

  1. Employee في WORKS_FOR مع Department.
  2. Department في نفس العلاقة (قسم جديد).
  3. Order في PLACES مع Customer.
  4. Customer في PLACES مع Order.
  5. Product في INCLUDES مع OrderItem.
  6. OrderItem في INCLUDES مع Product.
الإجابات

(7) Total (DeptID NOT NULL). (8) Partial (قسم من غير موظفين ممكن). (9) Total. (10) Partial (عميل جديد). (11) Partial. (12) Total.
