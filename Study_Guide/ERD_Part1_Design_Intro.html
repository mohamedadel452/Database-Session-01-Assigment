1) ليه ممنوع تكتب الجداول مباشرة؟ (سلايد 4 و 8)

التعريف: تصميم قاعدة البيانات هو عملية رسم "المخطط" للبيانات: إيه اللي هنخزنه، وإزاي مرتب، وإزاي بيرتبط ببعضه، وإيه القواعد اللي بتمنع البيانات الغلط.

التشبيه: بناء عمارة. لو بدأت تبني من غير خريطة هتحتاج تهدم وتعيد لما تلاقي إن السلم مش داخل في أي مكان. وتعديل الجداول بعد ما تتملي بملايين الصفوف أصعب وأغلى بكتير من تعديل رسم على ورقة.

-- الحل بعد التصميم: كل حقيقة في مكان واحد
CREATE TABLE Customers (CustomerId INT PRIMARY KEY, Name NVARCHAR(100), Phone NVARCHAR(20));
CREATE TABLE Products  (ProductId  INT PRIMARY KEY, Name NVARCHAR(100), Price DECIMAL(10,2));
CREATE TABLE Orders    (OrderId INT PRIMARY KEY, CustomerId INT NOT NULL REFERENCES Customers(CustomerId));
CREATE TABLE OrderItems(OrderId INT REFERENCES Orders(OrderId), ProductId INT REFERENCES Products(ProductId),
                        Quantity INT NOT NULL, PRIMARY KEY (OrderId, ProductId));
UPDATE Customers SET Phone = '0102' WHERE CustomerId = 1;   -- تعديل واحد في مكان واحد

ده معنى "No Redundancy" في سلايد 7. وهو بيمهد لـ Normalization اللي هتدرسه بعد كده، والـ ERD هو الخطوة اللي بتخليك توصل للتقسيم ده بشكل مرئي.

4) من المتطلبات للـ ERD: تقنية الأسماء والأفعال

الخطوة اللي كل المبتدئين بيتوهوا فيها: من أين أبدأ؟ خد وصف المتطلبات وحلله:

نص المتطلبات: "المتجر بيبيع منتجات، وكل منتج له اسم وسعر وكمية في المخزون. العميل بيسجّل بالإيميل ورقم التليفون، وبيقدّر يعمل أكتر من طلب. الطلب فيه تاريخ، وبيحتوي منتج أو أكتر بكمية لكل منتج. كل طلب ليه عنوان شحن."

الأسماء (Nouns)تصنيفهاالأفعال (Verbs)العلاقة

أسئلة لازم تسألها لنفسك أو للعميل لكل علاقة

  1. الكيان A ممكن يكون مرتبط بكام B كحد أقصى؟ (Cardinality)
  2. هل ممكن A يوجد من غير B؟ (Participation: حد أدنى صفر ولا واحد)
  3. إيه اللي بيعرّف الـ A بشكل فريد؟ (Key)
  4. هل الـ A ده بيتكرر في الحقيقة، ولا قيمة بسيطة (كيان ولا خاصية)؟
  5. لو B اتمسح، يحصل إيه لـ A؟ (Cascade/Restrict)

6) مدخل الـ ERD (سلايد 9 إلى 15)

الـ ERD (Entity-Relationship Diagram) رسم تخطيطي بيوضح الكيانات (اللي بنخزن عنها بيانات)، وخصائصها، والعلاقات بينها. دوره: لغة مشتركة بين المحلل والمبرمج والعميل قبل كتابة SQL، وتكتشف بيه التكرار والعلاقات الناقصة بسرعة.

الأنواع الأشهر للرسم (وفيها تصحيح مهم)

السلايدات بتستخدم Chen notation (مستطيل وبيضاوي ومعين)، وده المستخدم في الجامعات والامتحانات. لكن في شغل المشاريع والأدوات (dbdiagram و draw.io و SSMS Diagrams و DbSchema) غالباً بتشوف Crow's Foot: الكيان جدول بأعمدته جواه، والعلاقة خط، وطرفه بيبيّن العدد (شوكة الغراب = many).

نصيحة عملية: اتعلم التفكير بـ Chen (لأنه بيوضّح المفاهيم)، واتدرّب تقرأ Crow's Foot (لأنك هتقابله في الشغل). والمفاهيم واحدة: كيانات وعلاقات ومفاتيح وcardinality وparticipation.

الـ ERD مش: (1) مش Class Diagram (الـ class فيه methods وسلوك)، (2) مش الـ Schema نفسه (الـ ERD يوصف الأفكار، والـ schema تنفيذها)، (3) مش بيحل مشاكل الأداء (ده الـ physical design).

7) أسئلة أولية (إجاباتها تحت)

  1. إيه الفرق بين Conceptual و Logical design؟

  3. جدول فيه عمود Skills = "C#, SQL, Azure". إيه المشاكل؟
  4. مين بيعدّل الـ ERD لما المتطلبات تتغير؟
  5. هل الـ ERD بيشمل Indexes؟

الإجابات: (1) الـ conceptual أفكار بدون جداول، والـ logical جداول وPK/FK. (2) لا، ده snapshot تاريخي للسعر وقت الشراء. (3) مفيش بحث بالمهارة، مفيش integrity، مستحيل تعمل join، وصعب تحذف مهارة واحدة (non-atomic). (4) فريق التصميم مع الـ stakeholders، وأي تغيير بيعدّي على migration. (5) لأ، الـ indexes في الـ physical design. (6) لو ممكن طلب من غير منتج فهي partial participation من ORDER، وإلا total. والمشكلة اللي بتحصل لما الجدول الواحد يمنع إضافة منتج جديد من غير طلب هي insert anomaly.
