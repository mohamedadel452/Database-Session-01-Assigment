سلايدات 19 إلى 23: اختيار الـ PK والـ FK والتسمية والتخطيط للأداء. القرارات دي بتتاخد مرة واحدة وبتفضل معاك سنين، وتغييرها بعد وجود بيانات حقيقية مؤلم.

1) اختيار الـ Primary Key (سلايد 20)

السلايد بيدي ثلاث قواعد: اختر attribute يعرّف الصف بشكل فريد، استخدم surrogate key لو الـ natural keys معقدة أو بتتغير، وخلي الـ PK قصير ومستقر وNOT NULL. ليه "قصير" بالذات؟

في SQL Server الـ clustered key بيتحط في كل nonclustered index كمؤشر للصف. فلو الـ PK عبارة عن 4 أعمدة نصية (زي complex attribute في الجزء 2) أو GUID (16 بايت) بدل INT (4 بايت)، كل index هيبقى أكبر وأبطأ وأكلف في الذاكرة.

    EmpID INT IDENTITY(1,1) CONSTRAINT PK_Employees PRIMARY KEY,
    PublicId UNIQUEIDENTIFIER NOT NULL DEFAULT NEWID() CONSTRAINT UQ_Employees_PublicId UNIQUE,  -- يظهر في الـ API

مفاهيم خاطئة: (1) "الـ IDENTITY مضمون بلا فجوات": لأ، rollback وإعادة تشغيل بيعملوا فجوات. (2) "الـ GUID أحسن لأنه فريد عالمياً": يصلح لو IDs بتتولد من أنظمة متعددة، لكن كمفتاح clustered عشوائي هو بطيء. (3) "الـ PK لازم يكون بيانات مفهومة": العكس، المفتاح الجيد بلا معنى فلا يحتاج تغيير.

2) اختيار الـ Foreign Key (سلايد 21)

قواعد السلايد: FK بين الجداول، بيشاور على PK (أو candidate key) في الجدول الأب، وأسماء ذات معنى. وإضافات مهمة:

CREATE TABLE Employees (
    EmpID INT IDENTITY PRIMARY KEY,
    DepartmentID INT NOT NULL,
    CONSTRAINT FK_Employees_Departments FOREIGN KEY (DepartmentID)
        REFERENCES Departments(DepartmentID) ON DELETE NO ACTION ON UPDATE NO ACTION);
CREATE INDEX IX_Employees_DepartmentID ON Employees(DepartmentID);   -- SQL Server ما بيعملوش تلقائياً
ON DELETEEF Coreإمتىالخطر
NO ACTION / RESTRICTRestrictالافتراضي الآمن (عميل له طلبات)الحذف بيفشل لو فيه أبناء (مقصود)
CASCADECascade (الافتراضي للعلاقة الإجبارية)أبناء ملهمش معنى لوحدهمحذف جماعي بغلطة واحدة، ومسارات cascade متعددة مرفوضة
SET NULLSetNullعلاقة اختيارية (مدير اتحذف)لازم العمود nullable
SET DEFAULT-نادرلازم default صالح

مشاكل واقعية:

  1. Multiple cascade paths: جدول OrderItems بيشاور على Orders وعلى Products وكل واحد بيشاور على Customers بـ cascade: SQL Server بيرفض (خطر دورات). اجعل واحدة NO ACTION وانفذ الحذف من الكود أو بـ trigger.
  2. EF Core للعلاقة الاختيارية: الافتراضي ClientSetNull (بيصفّر الـ FK في الكيانات المحمّلة بس، والـ DB بيرفض لو فيه أبناء مش محمّلين). اكتب السلوك صراحة.
  3. مفيش index على FK: الحذف من الأب والـ joins بيعملوا scan على الابن. EF Core بيضيف index تلقائياً للـ FK، لكن SQL مكتوب يدوياً لأ.
  4. ON UPDATE CASCADE نادراً مطلوب: لأن الـ PK المفروض ما يتغيرش. لو محتاجه فالـ PK اتختار غلط.
modelBuilder.Entity<Employee>()
    .HasOne(e => e.Department).WithMany(d => d.Employees)
    .HasForeignKey(e => e.DepartmentID).IsRequired().OnDelete(DeleteBehavior.Restrict);

4) التخطيط للأداء والـ Indexes (سلايد 23)

الفكرة: الـ index زي فهرس الكتاب: بدل ما تقلّب كل الصفحات (table scan)، بتروح مباشرة للصفحة (index seek). التكلفة: مساحة، وكل INSERT/UPDATE/DELETE لازم يعدّل الـ indexes كمان.

النوعالاستخداممثال السلايد / عملي
Clusteredترتيب الجدول نفسه (واحد فقط)، غالباً الـ PKEmpID
Nonclusteredبحث بعمود غير PKEMPLOYEE(DeptID) لـ "موظفين القسم"
Compositeشرطين أو أكتر مع بعضOrders(CustomerID, OrderDate) لتاريخ طلبات عميل
Covering (INCLUDE)يغطي الاستعلام كله بلا key lookup(CustomerID, OrderDate) INCLUDE (Total)
Filtered / Uniqueجزء من الصفوف أو منع تكرارWHERE IsDeleted = 0
CREATE INDEX IX_Orders_Customer_Date ON Orders(CustomerID, OrderDate) INCLUDE (TotalAmount);

SELECT OrderID, OrderDate, TotalAmount FROM Orders
WHERE CustomerID = 42 ORDER BY OrderDate DESC;       -- seek على العميل والترتيب جاهز بلا sort

-- ترتيب أعمدة المركّب مهم (leftmost prefix):
--   يخدم: WHERE CustomerID = 42   |   WHERE CustomerID = 42 AND OrderDate > ...
--   لا يخدم: WHERE OrderDate > ...  (لوحده)
-- فـ index منفصل على CustomerID لوحده مكرر ومالوش لازمة

قاعدة اختيار العمود: الأعمدة المستخدمة في WHERE و JOIN و ORDER BY، والأولى هي الأعلى selectivity (قيم متنوعة). فهرس على Gender (قيمتين) نادراً يفيد.

5) أخطاء الأداء المتكررة

  1. دالة على العمود (non-sargable): 
    WHERE YEAR(OrderDate) = 2024                                        -- scan: الدالة بتمنع الـ index
WHERE OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01'        -- seek
  2. تحويل نوع ضمني: مقارنة عمود VARCHAR بـ NVARCHAR parameter ممكن يعمل scan. طابق الأنواع.
  3. Index على كل عمود: الكتابة بتبطأ والمساحة بتزيد. اقرأ الـ execution plan وادي أولوية للاستعلامات الفعلية، واحذف غير المستخدم (DMV: sys.dm_db_index_usage_stats).
  4. SELECT *: بتجيب أعمدة كبيرة وتمنع الـ covering. اختار الأعمدة.
  5. Deep paging بـ OFFSET: OFFSET 1000000 ROWS لازم يتخطى مليون صف. استخدم keyset: WHERE OrderID < @last ORDER BY OrderID DESC.
  6. N+1 في EF Core: حلقة بتنفذ query لكل صف. استخدم Include أو projection.

Partitioning والأرشفة: للجداول بمئات الملايين، قسّم بالتاريخ (partitions) أو انقل القديم لجدول أرشيف. ومتخطط له من البداية: PK مناسب (يشمل عمود التقسيم)، وأنواع بيانات صغيرة، وتجنب NVARCHAR(MAX) في الأعمدة اللي بتتفلتر.

6) صندوق أدوات الـ Constraints

CREATE TABLE Products (
    ProductID INT IDENTITY CONSTRAINT PK_Products PRIMARY KEY,
    Name  NVARCHAR(150) NOT NULL,
    SKU   NVARCHAR(30)  NOT NULL CONSTRAINT UQ_Products_SKU UNIQUE,
    Price DECIMAL(10,2) NOT NULL CONSTRAINT CK_Products_Price CHECK (Price >= 0),
    Stock INT           NOT NULL CONSTRAINT DF_Products_Stock DEFAULT 0 CONSTRAINT CK_Products_Stock CHECK (Stock >= 0));
modelBuilder.Entity<Product>().ToTable(t => t.HasCheckConstraint("CK_Products_Price", "[Price] >= 0"));

أضف قيد على جدول موجود فيه بيانات: ALTER TABLE ... WITH CHECK ADD CONSTRAINT يفحص الصفوف الحالية، ولو فيها بيانات مخالفة بيفشل. نضّف الأول.

7) أعمدة بتضيفها وقت التصميم (بدون ما الـ ERD يذكرها)

  • Audit: CreatedAt (UTC) و UpdatedAt و CreatedBy.
  • Soft delete: IsDeleted أو DeletedAt مع EF Core Global Query Filter، وانتبه إن UNIQUE لازم يبقى filtered index WHERE IsDeleted = 0.
  • Concurrency: RowVersion (rowversion) و IsRowVersion() في EF لمنع lost updates لما اتنين يعدّلوا نفس الصف.
public byte[] RowVersion { get; set; } = null!;
modelBuilder.Entity<Product>().Property(p => p.RowVersion).IsRowVersion();
// SaveChanges بترمي DbUpdateConcurrencyException لو الصف اتعدّل من حد تاني

8) تمارين (اضغط لكشف الإجابة)

  1. أصلح الأسماء: tblEmp(id, nm, dt, deptid) و Order(ID, Amt).
  2. الاستعلام: WHERE DepartmentID = 5 AND HireDate > '2024-01-01'. صمم index.
  3. جدول OrderItems بيشاور على Orders (ON DELETE ؟) وعلى Products (ON DELETE ؟).
  4. موقع بيعرض /users/1001. إيه الخطر وإيه الحل؟
  5. index على (CustomerID) وindex تاني على (CustomerID, OrderDate). إيه المشكلة؟
  6. الاستعلام WHERE LOWER(Email) = 'a@x.com' بطيء رغم index على Email. ليه؟
  7. PK جدول (Country, City, Street, ZIP). اذكر 3 مشاكل.
  8. جدول بـ 500 مليون صف، PK INT. إيه الخطر؟
الإجابات

(1) Employees(EmployeeID, EmployeeName, HireDate, DepartmentID) و Orders(OrderID, TotalAmount). (2) (DepartmentID, HireDate): المساواة أولاً ثم المدى. (3) Orders: CASCADE (البند ملوش معنى بلا طلب)، Products: RESTRICT/NO ACTION للحفاظ على تاريخ المبيعات. (4) enumeration/IDOR، الحل تحقق صلاحية + معرّف عام GUID. (5) الأول مكرر (leftmost prefix) وبيكلف كتابة، احذفه. (6) LOWER() على العمود بيمنع الـ seek. الحل collation غير حساس للحروف أو computed column مفهرس. (7) PK عريض بيكبّر كل index، قابل للتغير، نصوص بتتقارن ببطء. استخدم surrogate + unique. (8) INT حده 2.1 مليار، قرّب منه فلازم BIGINT مبكراً لأن تغييره بعد ذلك بيحتاج إعادة بناء كل الـ indexes والـ FKs.
